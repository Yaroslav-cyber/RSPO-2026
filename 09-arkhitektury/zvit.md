# Практична робота №09
## Архітектури: масштабування, яке можна виміряти

### 1. Мета роботи

Дослідити продуктивність різних архітектур клієнт-серверної взаємодії, порівняти роботу одного та декількох екземплярів служби, перевірити балансування навантаження, поведінку системи під час відмови вузла та використання спільного сховища.

### 2. Хід роботи

#### 2.1. Один вузол, один клієнт

На першому етапі було запущено один екземпляр служби A на порту `50007`. Для перевірки продуктивності використано одного клієнта, який надіслав 200 запитів.

Результати:

| Показник | Значення |
|---|---:|
| Кількість клієнтів | 1 |
| Кількість запитів | 200 |
| Успішних запитів | 200 |
| Помилок | 0 |
| Час виконання | 2,46 с |
| Пропускна здатність | 81 запит/с |
| Медіанна затримка | 10,56 мс |
| 95-й відсоток затримки | 21,64 мс |
| Максимальна затримка | 48,58 мс |
| Записів у журналі A | 200 |

Усі запити були успішно оброблені. Дані зберігалися безпосередньо в оперативній пам'яті екземпляра служби A.

#### 2.2. Один вузол під збільшеним навантаженням

На наступному етапі було досліджено вплив кількості одночасних клієнтів на продуктивність одного вузла. Кожен клієнт надсилав 50 запитів.

Результати вимірювань:

| Кількість клієнтів | Кількість запитів | Пропускна здатність | Медіанна затримка |
|---:|---:|---:|---:|
| 1 | 50 | 96 зап./с | 10,30 мс |
| 2 | 100 | 92 зап./с | 21,06 мс |
| 4 | 200 | 98 зап./с | 39,21 мс |
| 8 | 400 | 97 зап./с | 79,46 мс |

Під час експерименту пропускна здатність залишалася приблизно на одному рівні — від 92 до 98 запитів за секунду. Водночас зі збільшенням кількості клієнтів зростала затримка обробки запитів.

При восьми клієнтах медіанна затримка збільшилася до 79,46 мс. Це свідчить про те, що один екземпляр служби досяг межі своєї продуктивності: додаткові клієнти не збільшують швидкість обробки, а створюють чергу очікування.

#### 2.3. Два вузли за балансувальником

Далі було запущено два екземпляри служби:
- A — порт `50007`;
- B — порт `50008`.

Перед ними було налаштовано балансувальник, який приймав запити на порту `50000` та розподіляв їх між двома вузлами.

Для тестування використовувалися 8 клієнтів по 50 запитів кожен.

Результати:

| Показник | Значення |
|---|---:|
| Кількість клієнтів | 8 |
| Кількість запитів | 400 |
| Успішних запитів | 400 |
| Помилок | 0 |
| Час виконання | 2,61 с |
| Пропускна здатність | 153 зап./с |
| Медіанна затримка | 49,74 мс |
| 95-й відсоток затримки | 70,33 мс |
| Максимальна затримка | 90,03 мс |

Розподіл запитів між вузлами:

| Вузол | Оброблено запитів | Записів у журналі |
|---|---:|---:|
| A | 200 | 200 |
| B | 200 | 200 |

Балансувальник рівномірно розподілив навантаження між двома екземплярами. Пропускна здатність зросла з 97 до 153 запитів за секунду порівняно з одним вузлом під навантаженням восьми клієнтів.

Проте продуктивність не подвоїлася. Це пояснюється додатковими витратами на мережеву взаємодію та роботу балансувальника.

Важливою особливістю цієї архітектури є незалежність журналів: кожен екземпляр зберігає власні дані. Тому загальний стан системи розподілений між двома вузлами.

#### 2.4. Перевірка відмови одного вузла

На наступному етапі було перевірено поведінку системи під час аварійного вимкнення вузла B.

Для цього було запущено навантаження з 8 клієнтів, кожен з яких мав надіслати 200 запитів. Під час виконання тесту вузол B було зупинено вручну.

Результати:

| Показник | Значення |
|---|---:|
| Кількість запитів | 1600 |
| Успішних запитів | 1587 |
| Помилок | 13 |
| Час виконання | 17,87 с |
| Пропускна здатність | 89 зап./с |
| Медіанна затримка | 80,81 мс |

Помилки виникли через те, що частина запитів потрапила на вузол B саме під час його вимкнення.

Після виявлення відмови балансувальник виключив недоступний вузол із розподілу навантаження. Подальша обробка запитів продовжилася через вузол A.

Таким чином, перевірка доступності вузлів дозволяє системі продовжувати роботу навіть після відмови одного з екземплярів, хоча під час самого переходу можливі окремі помилки.

#### 2.5. Балансувальник без перевірки доступності

Для порівняння було запущено балансувальник із параметром `--bez-perevirky`, який вимикає перевірку доступності вузлів.

Вузол B залишався вимкненим, але балансувальник продовжував надсилати йому запити.

Результати:

| Показник | Значення |
|---|---:|
| Кількість запитів | 400 |
| Успішних запитів | 200 |
| Помилок | 200 |
| Час виконання | 56,64 с |
| Пропускна здатність | 4 зап./с |
| Медіанна затримка успішних запитів | 14,36 мс |
| 95-й відсоток затримки | 34,07 мс |

Половина запитів завершилася помилкою `ConnectionResetError`, оскільки вони були спрямовані до недоступного вузла B.

Порівняно з балансувальником, який перевіряє доступність вузлів, цей варіант працював значно гірше. Він витратив 56,64 секунди на 400 запитів, тоді як варіант із перевіркою доступності обробив 1600 запитів за 17,87 секунди.

Цей експеримент підтвердив важливість перевірки стану вузлів: без неї балансувальник продовжує надсилати запити до несправного екземпляра, що призводить до помилок і значного зниження продуктивності.

#### 2.6. Два вузли зі спільним сховищем

На цьому етапі було змінено архітектуру зберігання даних.

Було запущено окремий процес сховища на порту `50020`, після чого обидва екземпляри служби A та B були налаштовані на роботу з ним.

Таким чином, самі екземпляри служб більше не зберігали власний стан, а зверталися до одного спільного сховища.

Для перевірки використовувалися 8 клієнтів по 50 запитів.

Результати:

| Показник | Значення |
|---|---:|
| Кількість запитів | 400 |
| Успішних запитів | 400 |
| Помилок | 0 |
| Час виконання | 3,82 с |
| Пропускна здатність | 105 зап./с |
| Медіанна затримка | 69,72 мс |
| 95-й відсоток затримки | 130,41 мс |
| Максимальна затримка | 323,78 мс |

Результати перевірки стану:

| Компонент | Кількість записів у спільному журналі |
|---|---:|
| Вузол A | 400 |
| Вузол B | 400 |
| Спільне сховище | 400 |

Усі 400 запитів були успішно оброблені. Обидва екземпляри служби бачили один і той самий журнал із 400 записів.

Це означає, що дані більше не розподіляються між незалежними журналами різних екземплярів. Обидві копії служби працюють зі спільним джерелом даних.

Водночас продуктивність знизилася порівняно з архітектурою двох незалежних вузлів: зі 153 до 105 запитів за секунду. Додаткові звернення до окремого процесу сховища збільшують затримку обробки запитів.

#### 2.7. Перевірка відмови спільного сховища

На завершальному етапі було перевірено поведінку системи після вимкнення спільного сховища.

Обидва екземпляри служб A та B і балансувальник залишалися запущеними, але процес сховища на порту `50020` було зупинено.

Після цього було повторно запущено тест із 8 клієнтами по 50 запитів.

Результати:

| Показник | Значення |
|---|---:|
| Кількість запитів | 400 |
| Успішних запитів | 0 |
| Помилок | 400 |
| Час виконання | 0,17 с |

Обидва екземпляри служби залишалися запущеними, але не могли виконувати запити через відсутність доступу до спільного сховища.

Цей експеримент показав, що спільне сховище є єдиною точкою відмови (Single Point of Failure). Якщо воно стає недоступним, усі екземпляри служб, які від нього залежать, втрачають можливість обробляти запити.

### 3. Порівняння архітектур

За результатами експериментів можна порівняти основні конфігурації системи.

| Архітектура | Клієнтів | Запитів | Пропускна здатність | Медіанна затримка |
|---|---:|---:|---:|---:|
| Один вузол | 8 | 400 | 97 зап./с | 79,46 мс |
| Два вузли з балансувальником | 8 | 400 | 153 зап./с | 49,74 мс |
| Два вузли зі спільним сховищем | 8 | 400 | 105 зап./с | 69,72 мс |

Найвищу продуктивність показала архітектура з двома незалежними вузлами за балансувальником. Вона дозволила розподілити обчислювальне навантаження між двома екземплярами.

Архітектура зі спільним сховищем показала нижчу продуктивність через додаткові звернення до окремого процесу зберігання даних, але забезпечила єдине джерело правди для обох екземплярів.

Окремі експерименти з відмовами також показали, що:
- перевірка доступності вузлів дозволяє балансувальнику виключати несправні екземпляри;
- відсутність перевірки доступності призводить до великої кількості помилок;
- спільне сховище усуває проблему незалежних журналів, але саме стає критично важливим компонентом системи.

### 4. Вибір архітектури для сценарію A

**Сценарій A:** збір показань лічильників від 10 000 квартир один раз на добу. Більшість пристроїв надсилає дані протягом короткого проміжку часу, тому система повинна витримувати значне короткочасне навантаження та надійно зберігати всі отримані показання.

Для цього сценарію я обираю архітектуру з двома екземплярами служби за балансувальником і спільним сховищем.

Обґрунтування вибору:

1. Два екземпляри служби дозволяють розподіляти навантаження між вузлами. У проведеному експерименті два незалежні вузли забезпечили пропускну здатність 153 запити за секунду замість 97 запитів за секунду для одного вузла.
2. Спільне сховище забезпечує єдине джерело правди. Це важливо для сценарію, у якому показання всіх лічильників повинні зберігатися разом, незалежно від того, який екземпляр служби обробив запит.
3. Балансувальник із перевіркою доступності дозволяє виключати несправні вузли та продовжувати обробку запитів через доступні екземпляри.

У моєму тесті конфігурація зі спільним сховищем забезпечила 105 запитів за секунду та успішно обробила всі 400 запитів.

**Основна проблема обраної архітектури** — спільне сховище є єдиною точкою відмови. Експеримент підтвердив, що після його вимкнення всі 400 запитів завершилися помилками, хоча обидва екземпляри служби продовжували працювати.

Я змінив би своє рішення, якби вимоги до доступності системи стали настільки високими, що навіть короткочасна відмова сховища була б неприпустимою. У такому випадку необхідно було б додати резервне сховище, реплікацію даних та механізм автоматичного перемикання на резервний екземпляр.

### 5. Висновки

Під час практичної роботи було досліджено декілька варіантів побудови клієнт-серверної системи та порівняно їхню продуктивність за допомогою реальних вимірювань.

Було встановлено, що збільшення кількості клієнтів для одного вузла не забезпечує зростання пропускної здатності. Натомість збільшується затримка обробки запитів, оскільки один екземпляр служби має обмежену продуктивність.

Використання двох вузлів за балансувальником дозволило збільшити пропускну здатність зі 97 до 153 запитів за секунду. Також було перевірено поведінку системи під час відмови одного вузла та встановлено, що перевірка його доступності є важливою умовою стабільної роботи.

Використання спільного сховища дозволило об'єднати дані обох екземплярів служби в одному журналі. Проте додаткові звернення до сховища знизили продуктивність до 105 запитів за секунду. Окремий експеримент підтвердив, що відмова спільного сховища призводить до повної зупинки обробки запитів.

Для сценарію збору показань лічильників було обрано архітектуру з декількома екземплярами служби, балансувальником та спільним сховищем, оскільки вона поєднує розподіл навантаження з централізованим зберіганням даних.

Отже, під час вибору архітектури необхідно враховувати не лише максимальну продуктивність, а й місце зберігання даних, поведінку системи під час відмов та наявність єдиних точок відмови.
