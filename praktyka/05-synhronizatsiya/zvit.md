# Практична 05. Гонка даних

## Крок 1. Відтворення помилки

Спочатку було запущено оригінальну програму `zlamane.py` 10 разів.

Параметри запуску:

- Python 3.14.7
- процесор: AMD64 Family 23 Model 113 Stepping 0, AuthenticAMD
- 8 логічних процесорів
- Windows 11
- 4 процеси
- 20 000 замовлень на кожен процес
- початковий запас: 30 000

У результаті всі 10 прогонів мали порушення хоча б одного інваріанту.

Інваріант 1 порушувався у 8 із 10 прогонів. Залишок у таких випадках ставав від'ємним.

Інваріант 2 порушувався у всіх 10 прогонах. Значення `відвантажено + залишок` не дорівнювало початковому запасу 30 000.

Причиною є одночасна робота декількох процесів зі спільними даними.

## Крок 2. Пошук помилки

### Перша проблемна ділянка

Проблема знаходиться в операції:

```python
vidvantazheno.value = vidvantazheno.value + kilkist
```

На перший погляд це виглядає як одна операція, але насправді тут відбувається читання значення, додавання та запис нового значення.

Між цими діями інший процес може також прочитати старе значення та записати свій результат.

Наприклад, нехай `vidvantazheno = 100`.

Два процеси можуть одночасно отримати значення `100`. Перший процес хоче додати `3` і записує `103`, а другий хоче додати `2` і записує `102`.

У результаті фактично було відвантажено 5 одиниць, але у спільній змінній може залишитися значення лише `102`.

Це називається втратою оновлення.

Така ситуація порушує інваріант 2:

```text
відвантажено + залишок = початковий запас
```

### Друга проблемна ділянка

Інша проблема знаходиться між:

```python
if zalyshok.value >= kilkist:
```

та:

```python
zalyshok.value = zalyshok.value - kilkist
```

Між перевіркою та списанням інший процес може змінити значення `zalyshok`.

Наприклад, якщо залишилося 2 одиниці:

```text
Процес 1: перевіряє 2 >= 2 → True
Процес 2: списує 2 одиниці
Процес 1: списує ще 2 одиниці
```

У такій ситуації запас може стати `-2`.

Тому перевірка та списання повинні виконуватися разом, без можливості втручання іншого процесу.

Ця проблема порушує інваріант 1 та може вплинути на інваріант 2.

## Крок 3. Виправлення

Для виправлення було використано `multiprocessing.Lock`.

Перед створенням процесів створюється:

```python
zamok = mp.Lock()
```

Після цього `zamok` передається кожному процесу як аргумент.

Критична частина коду захищається:

```python
with zamok:
    if zalyshok.value >= kilkist:
        zalyshok.value = zalyshok.value - kilkist
        vidvantazheno.value = vidvantazheno.value + kilkist
        moi += kilkist
    else:
        vidmov.value = vidmov.value + 1
```

Тепер тільки один процес одночасно може виконувати цю частину коду.

Це гарантує, що між перевіркою залишку та його зміною інший процес не зможе змінити спільне значення.

Також оновлення `vidvantazheno` захищене тим самим блокуванням.

## Крок 4. Чому не можна блокувати весь цикл

Не можна ставити `Lock` навколо всього циклу обробки замовлень.

Наприклад, такий варіант був би неправильним:

```python
with zamok:
    for _ in range(ZAMOVLEN_NA_PROTSES):
        ...
```

У цьому випадку один процес захопив би блокування та виконав увесь свій цикл, поки інші процеси чекали б.

Тоді паралельне виконання фактично було б вимкнене.

Тому `Lock` використовується тільки для критичної частини, де процеси працюють зі спільними даними.

## Крок 5. Перевірка виправлення

Після виправлення спочатку було виконано 5 прогонів із 4 процесами та 20 000 замовлень на процес.

Результат:

```text
Без порушень: 5 із 5
```

У кожному прогоні:

```text
залишок = 0
відвантажено = 30000
```

Усі 4 процеси також виконували роботу.

Після цього навантаження було збільшено до 8 процесів та 100 000 замовлень на кожен процес.

Було виконано 10 прогонів.

Результат:

```text
Без порушень: 10 із 10
```

У всіх 10 прогонах залишок дорівнював `0`, а відвантажено було рівно `30000`.

Час виконання становив від `9.99` до `11.28` секунд.

## Крок 6. Розподіл роботи між процесами

Після виправлення робота розподілялася між усіма процесами.

Наприклад, у першому прогоні з 8 процесами:

| Процес | Відвантажено |
|---:|---:|
| 1000 | 4216 |
| 1001 | 4573 |
| 1002 | 3844 |
| 1003 | 3798 |
| 1004 | 3479 |
| 1005 | 3504 |
| 1006 | 3246 |

У сумі це дає 30 000 відвантажених одиниць.

Розподіл не є абсолютно однаковим, оскільки порядок виконання процесів залежить від планувальника операційної системи. Важливо, що всі процеси виконували роботу, а не один процес виконав весь цикл.

## Висновок

У початковій програмі виникала гонка даних через одночасну роботу декількох процесів зі спільними змінними.

Основними проблемами були операція зміни `vidvantazheno` та перевірка залишку разом із його списанням. Без синхронізації різні процеси могли одночасно прочитати та змінити одні й ті самі значення.

Для виправлення було використано `multiprocessing.Lock`. Критична частина коду була захищена блокуванням, але весь цикл обробки замовлень не блокувався.

Після виправлення було отримано 5 із 5 успішних прогонів при початковому навантаженні та 10 із 10 успішних прогонів при збільшеному навантаженні.

Отже, синхронізація усунула порушення інваріантів, при цьому паралельна робота процесів збереглася.
