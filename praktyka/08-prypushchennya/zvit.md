# Практична робота №08
## Зламати хибне припущення

### Мета роботи

Дослідити поведінку клієнт-серверної системи в умовах ненадійної мережі. Перевірити, як затримки, втрата відповідей та обриви з'єднання впливають на обробку запитів. Дослідити роботу повторних спроб і ключів ідемпотентності для запобігання дублюванню операцій.

---

### 1. Перевірка прямого з'єднання

Спочатку було запущено службу та клієнт без використання проксі.

Команда запуску клієнта:

```bash
python kliyent.py --kilkist 10
```

**Результат:**
- Успішно виконано 10 із 10 запитів.
- У журналі служби з'явилося 10 записів.
- Час виконання — 0,04 с.
- Помилок не виникло.

Отже, за звичайних умов клієнт отримує відповіді від служби, а кількість виконаних операцій відповідає кількості надісланих запитів.

### 2. Перевірка затримки мережі

Для перевірки впливу затримки було запущено проксі з параметром `--zatrymka 300`.

```bash
python nenadiyna_merezha.py --zatrymka 300
```

Клієнт надсилав запити через порт проксі:

```bash
python kliyent.py --port 50010 --kilkist 10
```

**Результат:**
- Успішно виконано 10 із 10 запитів.
- Служба зареєструвала 10 операцій.
- Загальний час виконання — 6,11 с.

Після цього експеримент було повторено з таймаутом 2 секунди:

```bash
python kliyent.py --port 50010 --kilkist 10 --taimaut 2
```

Результат залишився практично незмінним: 10 із 10 успішних запитів за 6,11 с.

**Висновок:** таймаут не прискорює мережу. Він лише обмежує час очікування відповіді. Якщо відповідь надходить раніше за встановлений таймаут, клієнт продовжує працювати у звичайному режимі.

### 3. Втрата відповідей

Наступним кроком було перевірено втрату відповідей від служби. Для цього проксі було запущено з параметрами:

```bash
python nenadiyna_merezha.py --vtratyty-vidpovid 0.5 --nasinnia 7
```

Команда запуску клієнта:

```bash
python kliyent.py --port 50010 --kilkist 10 --taimaut 2
```

**Результат:**
- Клієнт отримав успішні відповіді лише на 3 із 10 запитів.
- У журналі служби було зареєстровано всі 10 операцій.
- Загальний час виконання — 0,08 с.

Цей експеримент показав, що втрата відповіді не означає втрату самого запиту. Служба могла успішно виконати операцію, але клієнт не отримав підтвердження.

Таким чином, виникає невизначеність: клієнт не може точно знати, чи була операція виконана, якщо відповідь не надійшла.

### 4. Повторні спроби без ключів ідемпотентності

Для перевірки повторних спроб було використано той самий режим втрати відповідей, але клієнту дозволили виконувати до чотирьох спроб.

```bash
python kliyent.py --port 50010 --kilkist 10 --taimaut 2 --sprob 4
```

**Результат:**
- Успішно отримано відповіді на 9 із 10 запитів.
- Кількість додаткових спроб — 10.
- У журналі служби з'явилося 23 записи замість 10.
- Кількість зайвих записів — 13.
- Загальний час виконання — 4,15 с.

Повторні спроби допомогли клієнту частіше отримувати відповіді, проте спричинили дублювання операцій. Служба не могла визначити, що повторний запит відповідає операції, яку вона вже виконувала, тому кожного разу створювала новий запис.

### 5. Використання ключів ідемпотентності

Щоб усунути дублювання, було повторено попередній експеримент із додатковим параметром `--kliuch`.

```bash
python kliyent.py --port 50010 --kilkist 10 --taimaut 2 --sprob 4 --kliuch
```

**Результат:**
- Клієнт отримав успішні відповіді на 9 із 10 запитів.
- Кількість додаткових спроб — 10.
- У журналі служби залишилося рівно 10 записів.
- Кількість унікальних ключів — 10.
- Загальний час виконання — 4,17 с.

Ключ ідемпотентності дозволяє службі розпізнавати повторні запити. Якщо запит із таким ключем уже був оброблений, служба повертає попередній результат, не створюючи нову операцію.

Це дозволило уникнути дублювання, хоча клієнт усе ще не отримав одну з відповідей. Отже, ідемпотентність запобігає повторному виконанню операції, але не гарантує доставку відповіді.

### 6. Власний експеримент: обрив з'єднання до передачі запиту

Для власного експерименту було обрано режим обриву з'єднання до того, як запит потрапить до служби.

Проксі було запущено з параметрами:

```bash
python nenadiyna_merezha.py --obryv-vidrazu 0.5 --nasinnia 7
```

Клієнт працював із повторними спробами та ключами ідемпотентності:

```bash
python kliyent.py --port 50010 --kilkist 10 --taimaut 2 --sprob 4 --kliuch
```

**Результат:**
- Клієнт отримав успішні відповіді на 9 із 10 запитів.
- Кількість додаткових спроб — 10.
- Служба зареєструвала 9 операцій.
- Кількість унікальних ключів — 9.
- Загальний час виконання — 4,12 с.

На відміну від попереднього експерименту, у цьому випадку одна операція дійсно не дійшла до служби. Тому в журналі з'явилося 9 записів, а не 10.

Повторні спроби дозволили успішно передати більшість запитів. Оскільки невдалі спроби обривалися до обробки службою, дублювання операцій не виникло.

### 8. Висновки

Під час практичної роботи було досліджено поведінку клієнт-серверної системи за умов ненадійної мережі.

1. Встановлено, що таймаут обмежує час очікування відповіді, але не впливає на швидкість самої мережі.
2. Втрата відповіді не означає, що запит не був виконаний. У третьому експерименті клієнт отримав лише 3 відповіді, хоча служба зареєструвала всі 10 операцій.
3. Повторні спроби підвищують імовірність отримання відповіді, але без додаткового механізму захисту можуть створювати дублікати. Це підтвердив результат із 23 записами замість 10.
4. Ключі ідемпотентності дозволяють розпізнавати повторні запити та повертати попередній результат без повторного виконання операції. Завдяки цьому кількість записів залишилася рівною 10.
5. Ключ має бути однаковим для всіх повторів однієї логічної операції. Служба повинна перевіряти його перед створенням нового запису.
6. Власний експеримент показав різницю між втратою відповіді та обривом до передачі запиту: у першому випадку операція вже могла бути виконана, а в другому вона взагалі не потрапляла до служби.
7. У власному клієнті таймаут і повторні спроби залежать від параметрів запуску. Якщо таймаут не задано, з'єднання може очікувати відповідь без встановленого обмеження часу; якщо кількість спроб не збільшено, клієнт не виконує додаткових повторів.

Отже, головний висновок роботи полягає в тому, що відсутність відповіді не дозволяє однозначно визначити результат операції. Для надійної роботи клієнт-серверних систем важливо використовувати таймаути, повторні спроби та ключі ідемпотентності.
